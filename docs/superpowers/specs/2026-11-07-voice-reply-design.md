# 回复消息时不定时发语音：设计说明

日期：2026-11-07　状态：用户已确认规则（2026-11-07），待拆实现步骤

## 1. 目的

让囡囡在回**群聊**消息时（私聊不发语音），偶尔用自己的声音（百炼复刻音色）回一句，显得更像真人。原则是**少而准**：只在合适的场合、合适的时间、按概率发；发多了会烦人，也容易出错。

已有基础：`src/action/voice_sender.py`（合成并发送语音条）、定时推送里的语音（`src/bot/scheduled_push.py`，含 `voice_styles` 和语速浮动），链路原理见 `docs/sound-record.md`。

## 2. 目标 / 非目标 / 反目标

**目标**
- 三种场合（被夸感谢、斗嘴调侃、安慰）按概率主动发语音。
- 有人要听语音时傲娇：不是一叫就有，越坚持越容易答应。
- 所有数值放配置文件，可调；有观察期（只记录、不真发）。

**非目标**
- 不做语音识别（别人发的语音怎么听）。
- 不改定时推送的语音逻辑。
- 不做每日上限和冷却（用户明确不要）。
- 私聊不发语音（用户决定）。

**反目标（出现这些就算失败，即使功能「能跑」）**
- 语音发错聊天，或发到静默白名单以外的聊天。
- 在 22:00 以后、8:00 以前发语音。
- 语音里念出 @某某、链接、数字、英文。
- 语音失败导致这次回复丢失（必须改发文字兜底）。
- 拖慢正常文字回复：没触发语音的回复，耗时和行为与现在完全一致。

## 3. 用户已确定的规则

### 3.1 怎么发
- **语音代替文字**，不是文字 + 语音各发一条。
- **心情由 LLM 生成回复时一起给出**；style 从 `voice_styles` 按心情随机选（与定时推送一致）。
- **语速按字数动态控制**（用户决定）：字数越少越接近 0.9，越多越接近 1.2。按去掉 @ 和标点后的字数 n 线性计算：`rate = 0.9 + (min(n, 20) - 1) / 19 × 0.3`（1 字 0.9，20 字 1.2）。再叠加 `voice_rate_jitter` 随机浮动，结果限制在 [0.9, 1.2]（浮动叠加和限制范围是我的取值）。
- **失败改发文字**：合成或发送失败，同样的内容用文字发出。
- **聊天记录里标成 `[语音] 内容`**，让后续对话知道自己说过什么。

### 3.2 何时发
硬条件：
- **仅群聊**。
- **仅 8:00–22:00**（含 8:00，不含 22:00）。时间外一律文字。
- **语音文本必须不超过 20 字**（去掉 @ 后），超过的不用语音。

**主动发**（三种场合，全部满足才掷概率）：
1. 在时间窗口内；
2. LLM 标注的场合为 `被夸感谢` / `斗嘴调侃` / `安慰` 之一；
2a. LLM 给的心情在白名单内：撒娇、调皮、开心、安慰、惊讶（用户决定要限定；具体名单沿用讨论时的建议）；
3. 回复只有 1 条，去掉 @ 后不超过 20 字；
4. 内容可念：不含链接、数字、英文字母、emoji；
5. 囡囡在这个聊天里的上一条回复不是语音；
6. 按场合概率：被夸感谢 0.15、斗嘴调侃 0.15、安慰 0.2。

**被要求**（场合 `要听语音`，由 LLM 判断）：
- 程序记录同一个人在 10 分钟内要了第几次，答应概率依次 0.3 / 0.6 / 0.9（第 3 次及以后 0.9）。
- LLM 在这种场合一次给两句：`replies` 里是拒绝的话（文字），`voice.accept` 是勉强答应的话。掷中 → 把 `accept` 作为语音发；没中 → 发拒绝文字。
- 不受心情白名单、「上一条不是语音」的限制，但仍受群聊、时间窗口、**20 字**和「内容可念」限制。
- 掷中但 `accept` 超过 20 字或不可念：本次按没答应处理，发拒绝文字，计数不清零（我的取值：避免说了「就一句哦」却没有语音）。
- 时间窗口外：照发拒绝文字，不发语音，也不计次数。
- 答应后该人的计数清零。

### 3.3 场合定义（写进 prompt）

| 场合 | 算 | 不算 |
|---|---|---|
| 被夸感谢 | 对方夸囡囡（「囡囡好可爱」「你真厉害」）或谢谢她（「谢啦」「多亏你」） | 夸别人；客套的「辛苦了」；反讽（「你可真行啊」） |
| 斗嘴调侃 | 对方逗她、损她、开玩笑，她回嘴 | 真吵架、有火药味；多人起哄；严肃争论 |
| 安慰 | 对方说自己累了、难过、输了、抽卡歪了，她安慰 | 只是吐槽游戏机制；问怎么解决问题 |
| 要听语音 | 对囡囡说想听她声音、让她发语音（「发个语音」「来句语音」「想听你声音」「说句话听听」） | 让别人发语音；讨论语音功能本身；只是提到「语音」两个字 |
| 无 | 其他所有情况（绝大多数） | |

## 4. 设计

### 4.1 LLM 输出格式
在现有 `{"replies": [...]}` 上加可选字段 `voice`：

```json
{"replies": ["哼，算你有眼光"], "voice": {"scene": "被夸感谢", "mood": "调皮"}}
{"replies": ["哼，才不给你听"], "voice": {"scene": "要听语音", "mood": "不情愿", "accept": "好啦好啦，就一句哦"}}
{"replies": ["今晚八点开打"]}            // 不带 voice 等同 scene=无
```

- `scene` 只能取上表 5 个值；`mood` 只能取 `MOODS` 的 12 个；非法值一律当作「无」，不报错、不影响文字回复。
- 只读取**首次生成**的 `voice`。Self-Refine 的 Iterate 改写了回复时，`scene`/`mood` 沿用，但对改写后的文本**重新检查**第 3、4 条硬条件。
- prompt：**不改** `data/persona.md`。启用时把 `prompts/voice_reply.md`（场合定义、输出格式、示例）追加到**群聊**的 system prompt 末尾；未启用或私聊时 system prompt 与原来逐字相同。`prompts/voice_reply.md` 缺失时回复语音整体不启用。`prompts/iterate.md` 不变。（实现时调整，2026-11-07）

### 4.2 模块划分
- **新增 `src/reply/voice_policy.py`**：纯逻辑，不碰微信。
  - `load_voice_reply_config(path)`：读配置并校验，非法项启动时报 ❌ 并按默认值处理。
  - `VoiceReplyPolicy.decide(chat, sender, replies, voice_meta, now) -> VoiceDecision`：返回 `send_voice`、`text`、`mood`、`reason`（为什么发/不发，写日志）。内部维护：每个聊天「上一条是否语音」、每个人的要求次数和时间（内存中，重启清零）。
  - `strip_mentions(text)`：去掉 @某某 和 @所有人。
  - `is_speakable(text)`：链接、数字（含中文数字以外的阿拉伯数字）、英文字母、emoji 检查。
- **`src/reply/generator.py`**：`_parse_replies` 之外额外解析 `voice` 字段，存到 `self.last_voice_meta`（与现有 `last_*` 字段同一风格，`generate()` 返回值不变）。
- **`src/bot/wechat_bot.py`** 逐条发送那段（约 610 行）：
  1. 生成后调用 `policy.decide(...)`；
  2. `dry_run=true`：只写日志 `[VoiceReply] 本会发语音: …`，照常发文字（要求场合发拒绝文字）；
  3. 真发：先检查是群聊、该聊天允许发送（静默白名单，与 `sender.send` 的判断一致）→ 用 `ChatOpener` 校验当前窗口就是该聊天 → 按字数算基础语速，`realize_voice_line` 得到 style 和浮动后的语速（限制在 [0.9, 1.2]）→ `VoiceSender.send(...)`；
  4. 任一步失败 → 改用 `sender.send` 发同样的文字；
  5. 成功 → `sent_replies` / pending / 记忆里记为 `[语音] 内容`。
- **复用**：`voice_styles`、`voice_rate_jitter` 直接读 `data/scheduled_messages.json`（全项目只维护一份）。`realize_voice_line` 从 `scheduled_push.py` 复用。

### 4.3 配置文件（新增 `data/voice_reply.json`，重启生效）

```json
{
  "enabled": true,
  "dry_run": true,
  "hours": [8, 22],
  "max_chars": 20,
  "rate_by_length": [0.9, 1.2],
  "moods": ["撒娇", "调皮", "开心", "安慰", "惊讶"],
  "scenes": {"被夸感谢": 0.15, "斗嘴调侃": 0.15, "安慰": 0.2},
  "request": {"window_minutes": 10, "probabilities": [0.3, 0.6, 0.9]}
}
```

- `moods` 只约束三种主动场合；`要听语音` 不受限制。
- 私聊直接跳过，不调用 `decide`、也不计要求次数。
- 文件不存在或 `enabled=false`：完全不启用，prompt 也不要求输出 `voice`（保证行为与现在一致）。
- 初版 `dry_run=true` 上线观察，确认 LLM 标注准确后由用户改为 `false`。

### 4.4 日志
- 每次有 `voice` 标注都记一行：`[VoiceReply] chat=… sender=… scene=… mood=… decision=发/不发 reason=…`，方便观察期统计标注准确率。
- 真发时沿用 `[VoiceSender]` 日志（含实际 style/语速）。

## 5. 风险与待验证

1. **感知层怎么识别自己的语音条**：当前用视觉识别截图，语音条在屏幕上是「4″」这样的气泡。需在实现第一步用一张含语音条的截图确认它被识别成什么（文字「4″」/ 其他类型 / 被忽略），避免：被当成新消息、或让「上一条是否语音」判断失真。若识别成奇怪的文字，需在感知层把自己的语音条归一化。
2. **主循环阻塞**：发一条语音约「合成 1–3 秒 + 语音时长 + 3 秒」。概率低，可接受。
3. **右 Option 和麦克风**：发送期间按住右 Option、默认输入临时切到 BlackHole（见 `docs/sound-record.md`）。
4. **LLM 标注不准**：用观察期兜底；程序侧的硬条件保证即使标错也不会念出链接/数字或在夜里发。
5. **prompt 变长**：多了场合定义，每次生成会多一些输入 token。

## 6. 测试
- `voice_policy`：私聊不发、心情白名单、语速按字数（1 字 0.9、20 字 1.2、浮动后不超出范围）、要求场合 `accept` 超 20 字按拒绝、时间窗口边界（7:59 / 8:00 / 21:59 / 22:00）、字数含 @ 去除、可念检查、各场合概率（注入随机数）、上一条是语音时不发、要求计数（窗口内递增、超窗重置、答应后清零、时间外不计次）、非法 scene/mood 当作无、配置校验。
- `generator`：`voice` 字段解析（缺失、非法、只取首次生成）。
- `wechat_bot` 发送段：dry_run 只记日志；真发成功记 `[语音]`；语音失败改发文字；非白名单聊天不发语音；窗口校验失败改发文字。
- 观察期用真实日志核对标注准确率，再决定开 `dry_run=false`。

## 8. 用户确认记录（2026-11-07）
- 只在群聊发。
- 主动场合要限定心情。
- 先 `dry_run` 观察。
- 语音文本一律不超过 20 字，超过不用语音；语速按字数在 0.9～1.2 之间动态调整。
